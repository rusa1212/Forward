# 5주차 파트별 작업 우선순위

`docs/5th_wk` 표를 기준으로 파트(DB/BE/FE/PM)별로 묶고, 우선순위(P0 → P1) 순으로 재정렬했습니다.
P0는 이번 주 반드시 완료해야 하는 작업, P1은 P0 완료 후 여력이 있을 때 진행하는 작업입니다.

---

## DB

| 순위 | 우선순위 | 중분류 | 세부 작업 | 선행 작업 | 완료 기준 / 산출물 |
| :---: | :---: | --- | --- | --- | --- |
| 1 | P0 | 스키마 점검 | 기존 테이블 컬럼·타입·NULL 허용 여부·PK/FK 관계를 실제 기능 기준으로 최종 점검 | 4.2 | BE 전체 기능 개발에 필요한 DB 구조 확정 |
| 2 | P0 | 무결성/중복 방지 | 공고, 사용자 키워드, 저장공고, 알림 이력의 UNIQUE/FK 제약조건 적용 | 스키마 점검 | 중복 저장 및 관계 오류 방지 |
| 3 | P0 | 보안/RLS | Supabase RLS 및 사용자별 데이터 접근 정책 점검·적용 | 스키마 점검 | 사용자가 본인 개인화 데이터만 접근 가능 |
| 4 | P0 | 데이터 품질 | API 적재 공고의 중복, NULL, 날짜 형식, 상태값, 링크 등 데이터 품질 검증 | 4.6 (외부 API 연동) | 화면 노출 가능한 수준의 공고 데이터 품질 확보 |
| 5 | P1 | 성능(인덱스/쿼리) | 공고 검색·상태·기관·마감일, 사용자 키워드/저장공고 조회용 인덱스 및 쿼리 점검 | 스키마 점검 | 주요 조회 기능의 응답 지연 없이 동작 |

## 전체 흐름 요약

1. **DB** 스키마·무결성·RLS·데이터 품질(P0)을 먼저 확정해야 BE 개발이 막히지 않음. 인덱스 최적화(P1)는 병행 가능.
2. **BE**는 로그인 → 공고 조회 → 개인화(CRUD) → 대시보드 집계 → 키워드 매칭 → API 안정화 순으로 P0를 완료한 뒤, 마이페이지·알림/이메일·스케줄러(P1)를 이어서 진행.
3. **FE**는 공통 API Client/인증 연동을 최우선으로 깔고, 그 위에 인증 → 공고 → 개인화 → 대시보드 → 통합 점검(P0)을 쌓은 뒤 마이페이지·알림 UI(P1)를 마무리.
4. **PM**은 주 내내 일정/완료기준을 관리하다가, FE 통합 점검 이후 중간 시연으로 이슈를 확정하고 주 후반 개발 범위를 동결.
